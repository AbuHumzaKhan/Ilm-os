# Development Rules

## 1. One Current Objective

At any point, there must be one clearly defined immediate objective.

## 2. Evidence Before Change

Before changing architecture or implementation, inspect the current repository state and verify the reason for the change.

## 3. Small, Verifiable Steps

Prefer small changes that can be tested and understood independently.

## 4. No Feature Drift

Do not implement ideas simply because they are interesting. Record them in `FUTURE.md` or `DECISIONS.md` first.

## 5. Engine Before Scale

The reusable Learning Engine must be validated before creating dozens of skill libraries.

## 6. Real Learning Over Content Volume

A skill is not complete because it has many lessons. It must enable the learner to understand, practice, apply, and demonstrate the skill.

## 7. Real-World Relevance

Examples and projects should represent realistic work wherever practical.

## 8. AI Must Be Grounded

AI tutoring should use the current skill, lesson, exercise, learner state, and available evidence rather than inventing arbitrary curriculum content.

## 9. No Hidden State

Important architectural and product decisions must be documented.

## 10. Keep the Project Understandable

Folder structure, naming, interfaces, and documentation should make the project understandable to a new contributor.

## 11. Quality Gates

A milestone is complete only after its acceptance criteria and relevant tests are satisfied.

## 12. Maintain the Tracker

After meaningful work, update `CURRENT_STATUS.md`, roadmap state, and decision records when applicable.
